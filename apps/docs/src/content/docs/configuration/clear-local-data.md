title: "Clear local data"
description: "Understand the destructive reset before typing the confirmation word."

  order: 12
---

Open **Settings → Account → Danger zone → Clear local data**. The confirmation dialog lists what will be removed, then requires typing `clear`; the action is irreversible, and the dialog says so.

The current command empties fifteen SQLite tables, including chat messages, conversations, profiles, transcriptions, terms, hotkeys, API keys, preferences, styles, app targets, paired devices, pending audio deletions, daily word totals, their usage-event ledger, and the saved pill position. It deletes managed transcription audio and orphaned WAVs, clears the app-managed `storage/` directory, removes database quarantine backups and any staged Voquill migration artifacts, deletes the original `voquill.db` along with its SQLite sidecar files (`voquill.db-wal`, `voquill.db-shm`, and `voquill.db-journal`) from the matching sibling Voquill config directory, writes a `not_needed` reset marker to `voquill-migration-state.json` so leftover Voquill assets are not automatically re-imported on the next launch, and attempts to vacuum the database. Separate Voquill asset directories (`models/`, `transcription-models/`, `transcription-audio/`, and `storage/` under the Voquill data directory) are **not** deleted by this reset. It also clears app-owned browser storage such as the profile photo, onboarding flags, pending transcription deletes, and per-tool approvals. Signed-in session keys remain because clearing local data does not sign out. If mausVoice cannot stop recording or keyboard monitoring, it does not start the wipe in that attempt. The dialog reports the failure and offers a retry. If a later cleanup step fails, some data may already have been removed; local writes stay blocked while you retry. Vacuum is best effort after deletion. Use this for a genuine local reset, not as the first response to a provider outage, permission problem, or one bad style.

Before confirming, fully quit Voquill if you still want a backup of its database. Copy the original `voquill.db` together with any remaining SQLite sidecar files (`voquill.db-wal`, `voquill.db-shm`, and `voquill.db-journal`) from the matching sibling Voquill config directory, then confirm the reset. Also copy any history text you need, and note shortcuts, provider selections, writing styles, app-target settings, and other preferences that will need to be rebuilt. The reset clears the app-managed `storage/` directory and managed transcription audio as well as the listed database tables, but it does **not** delete `mausvoice.db` itself, downloaded models, log files, or the separate Voquill asset directories. Startup also writes an operational `bridge-server.json` containing only the loopback bridge port; it is regenerated on launch and is not user content. The reset does not undo operating-system integrations such as compositor hotkey bindings or the Java Access Bridge entry in `~/.accessibility.properties`; those are stored outside mausVoice's data directories. Inspect the documented data directories and relevant system settings separately if the goal is complete removal. This is application-level cleanup, not secure whole-disk erasure.

mausVoice stores API credentials locally in encrypted form, and this action clears their database rows, but account-side keys remain valid until you revoke them at the provider. Clearing local data is not key rotation. If a credential may be exposed, revoke it in the provider console even after resetting mausVoice.
