The reference pages state what a control does. These guides show you where it sits, what it looks like at each stage, and what happens next. Every figure is a capture of the shipped interface, in the theme you are reading, with numbered markers keyed to the list beneath it.

Three conventions apply to every guide in this section.

- A marker sits on the element it describes, at that element's top-left corner. A marker with a line under it marks a region rather than a control.
- The figure caption states the precondition. A review panel, for example, only appears when **Review before insert** is on.
- Light and dark are captured separately. If a colour or hairline looks wrong in one theme, the other theme shows what the value was meant to be.

<Callout title="Why captured figures and not one screenshot">
  A single screenshot freezes one window size, one theme, and one version. These figures are captured per theme from the same tokens the app draws with, they stay legible at any width, and the capture script lives beside them, so a surface change is a one-command refresh rather than a scavenger hunt for a stale image.
</Callout>

## Regenerating the figures

The figures are generated from `apps/docs/scripts/figure-stage.html` by `apps/docs/scripts/capture-guides.mjs`. The script drives headless Chromium over the DevTools protocol and writes both themes into `apps/docs/public/guides/`.

```bash
pnpm --filter docs figures
```

Run it after any change to a surface the guides show. The stage file and the captures are committed together, so a review can diff what changed.
