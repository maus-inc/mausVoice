Assistant mode is an experimental command workflow, separate from ordinary dictation. The recognized command becomes a chat message instead of a cleaned-up transcript. The conversation appears in the pill and under **Chats** in the main navigation.

This guide covers the parts that are easy to miss: where the switch lives, what a permission prompt is really asking, what power mode adds, and what happens when an agent's Paste meets the review panel.

## Configure it

<Steps>
  <Step
    title="Open Settings → AI and models → Assistant"
    image="assistant-step-1-settings"
    alt="The Assistant mode dialog with its provider segment, Assistant hotkey, Assistant mode, and Power mode rows"
  >
    The **Assistant mode** row opens a dialog whose title carries a Beta chip. Inside it, the provider configuration sits above three settings: **Assistant hotkey**, **Assistant mode**, and **Power mode**. Assistant mode is off by default, and nothing in the assistant runs until you turn it on.
  </Step>
  <Step
    title="Choose a generative credential"
    image="assistant-step-2-provider"
    alt="The assistant provider set to API with a credential selected"
  >
    Set the assistant provider to **API** and pick a credential whose provider supports generative text. **Off** leaves the assistant without an LLM backend, so a command has nowhere to go. The API segment also carries **Maximum iterations**, **Permission timeout (seconds)**, and the **Enabled tools** list. The assistant has its own provider selection. Changing the transcription provider or the post-processing provider does not move it.
  </Step>
  <Step
    title="Set the assistant hotkey"
    image="assistant-step-2-hotkey"
    alt="The pill recording an assistant command"
  >
    The assistant hotkey is separate from the dictation shortcut. Hold it, speak, and release, the same way as dictation. The voice is transcribed with the active transcription configuration, but the recognized text becomes a chat message rather than a History row.
  </Step>
  <Step
    title="Watch the tool steps"
    image="assistant-step-3-tools"
    alt="A completed tool step above a pending Paste request"
  >
    A command can take several model and tool steps. A finished step stays in the transcript as a dimmed line, and the step that needs you becomes a card. Allow covers that one call. Always Allow covers later calls of the same tool in the same conversation, and nothing else. A conversation is not finished after the first response.
  </Step>
</Steps>

## Permission prompts

The built-in tools can read the focused field and surrounding screen context, paste into the focused field, and close the pill conversation. A permissioned request offers **Deny**, **Allow**, and **Always Allow**. The card stays open for the permission timeout, 60 seconds by default, and a card nobody answers is denied rather than approved.

  ]}
/>

<Callout title="Always allow is scoped to one conversation">
  The approval is stored per tool and per conversation, not per command, and it survives a restart. A new conversation asks again, because a grant made while one task was running should not silently authorise the next. Clear local data removes these saved approvals from app-owned browser storage.
</Callout>

## Power mode

Power mode adds the `run_terminal_command` tool. The Rust backend validates each command against an allowlist and runs it directly, without a shell. Shell metacharacters such as `/`, `\`, `;`, `|`, `&`, and `$` are rejected anywhere in an argument, a bare `..` argument is refused, and absolute paths and subdirectory paths are not allowed. Enabling it takes a warning confirmation, and the Power mode row asks you to restart mausVoice before the tool can run. Start a new conversation after the restart.

Commands run with the mausVoice process's full user permissions. Keep power mode off unless the task genuinely needs shell access, and never approve a command you do not understand. The [assistant mode reference](../using-mausvoice/assistant-mode/) lists the exact allowlist for each platform.

## How a review reaches an agent's Paste

When the assistant's Paste tool is the thing that needs the transcript, the same review panel appears. The difference is the open icon in the header. For an agent Paste it saves a pending card in **Chats** instead of inserting, because opening the main window changes focus and the original target is gone. A dictation review uses the same icon to open the desktop composer.

<Steps>
  <Step
    title="The Paste tool asks, the panel opens"
    image="assistant-paste-review"
    alt="The review panel opened by the Paste tool"
  >
    The Paste tool reports Copy, Open, expiry, and failure back to the assistant, so the conversation knows what you decided instead of assuming the paste happened.
  </Step>
  <Step
    title="Open saves instead of inserting"
    image="assistant-step-4-open"
    alt="The saved pending card holding the reviewed text"
  >
    The text is saved as a pending card in Chats. This is the honest outcome when focus has moved, because a paste into a window that is no longer focused would land in the wrong place.
  </Step>
  <Step
    title="Copy from the card"
    image="assistant-step-5-copy"
    alt="The pending card with its text and a copy action"
  >
    Open Chats, copy the text from the card, and paste it into the application you want. The review is finished at that point. Nothing is retried in the background.
  </Step>
</Steps>

## What the assistant does not do

- It does not change your transcription or post-processing provider.
- It does not insert anything without a decision, except through an approved Paste tool.
- It does not keep a tool approval you cleared with **Clear local data**.
