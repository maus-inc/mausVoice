# PR 288 visual audit — in progress

## Scope and evidence

The PR changes the routed settings surface (Overview, Dictation, AI and models, Shortcuts, Appearance, Privacy and data, System and Account), account/profile and destructive dialogs, shared rows and theme consumers. The QA artifacts branch capture predates the current tooltip and layout changes; it is useful as historical evidence, not as proof of the current head.

A Chromium browser rendered the production-component desktop preview in a populated workspace. The first pass captured **240 images**: eight settings pages × five viewport sizes (1440×900, 1280×720, 1024×768, 800×600 and 640×480) × light/dark × top, bottom and search views. These are combinations, not 240 independently designed edge cases; searches in particular repeat the same query. The 640×480 viewport is below the native window minimum (800×600), but approximates the reduced CSS viewport available at higher zoom. The first pass was captured while the compact-rail fix was being developed, so it is not a clean before/after baseline for that fix.

A second pass captured **100 images**: profile, clear-data, delete-account and shortcut dialogs in two states, plus tooltip hover/focus, at the same five sizes and two themes. The profile name was changed to an unusually long value; destructive confirmation phrases were typed but the destructive actions were not executed. These are combinations inspired by the issues below, **not** 100 separate external issues. Both capture passes reported zero uncaught page errors. Screenshots and the capture scripts are temporary sandbox artifacts, not checked into the repository.

Selected images were inspected at full size and contact-sheet scale; capture count must not be confused with a full visual sign-off of every image. The tooltip's arrow center was within 0.5 CSS pixels of its info icon in the ten measured hover captures. Keyboard focus, real scrollability, translations, larger text, native desktop rendering, all other changed theme consumers and screenshots after each fix still require systematic coverage. No claim of zero visual regressions is made.

## Findings and fixes

1. At 800×600, the selected item in the horizontal settings rail could be outside its scroll viewport. The selected item is now revealed on route changes and window resize. A fresh Chromium capture at 800×600 shows Account in view; unit tests cover both directions and the no-scroll cases.
2. At 800×600, wide segmented controls squeezed settings descriptions into narrow columns. Non-interactive control rows now wrap when the text needs room; a fresh Appearance capture shows the description spanning the card with the control below it. Wide cards retain the existing side-by-side layout.
3. At 640×480, the profile dialog's form prevented its content from shrinking, clipping the footer. The form is now a shrinkable flex column, letting the dialog body scroll while keeping the actions visible. A fresh capture shows the Save button inside the dialog bounds; the content's scroll height exceeds its client height.

The local visual check uses a browser preview, not a native macOS/Windows/Linux window. A complete re-capture and visual review at the final head is still needed.

## Research and issue-derived checks

- [Apple: Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos) — density, resizing and keyboard use are desktop requirements.
- [Apple: Inclusive design](https://developer.apple.com/videos/play/wwdc2021/10275/) — explicitly inspect truncation and clipping at larger text sizes.
- [NN/g: Progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/) — keep frequently needed options discoverable and make transitions to secondary controls clear.
- [Atlassian: Tooltip usage](https://atlassian.design/components/tooltip/usage/) and [positioning](https://atlassian.design/server/components/tooltips) — focusable triggers, nonessential copy, and collision-aware placement.
- [Carbon: Dialogs](https://www.carbondesignsystem.com/building-blocks/core/patterns/dialogs) — clear actions and focus management for modal tasks.
- [VS Code #53255](https://github.com/microsoft/vscode/issues/53255) — settings cropping under zoom.
- [QuickAdd #1888](https://github.com/chhoumann/quickadd/pull/1888) — dialog action clipping at short window heights.
- [Meridian Flow #811](https://github.com/haowjy/meridian-flow/pull/811) — settings controls overflowing and descriptions becoming cramped in narrow desktop windows.
- [Mastodon #450](https://github.com/fedibird/mastodon/issues/450) — clipping near responsive breakpoints; hiding overflow is not a fix for incorrect layout.

## History import and retranscription

A History dialog pass, following the desktop keyboard-and-labelling scope in [GLOW #146](https://github.com/Community-Access/glow/issues/146), found that Import audio's Style and Language selects had visible labels but no programmatic association. Retranscribe used the same pattern. Both dialogs now connect their existing labels to the selects, with regression tests. Import's shared title-with-close also included the close button's accessible name in the dialog name; its shared title component now labels the dialog from the title content alone, preserving the close button as a separate control. Tests check the unique title reference and both select labels. In browser preview, open-dialog axe checks returned zero violations for both Import and Retranscribe, the Import dialog's exact accessible name matched its title, and Escape closed the dialogs; actual screen-reader behavior remains unverified.

Import's dialog and both selector menus were inspected at 800×600 and at 400×300 CSS pixels. At the smaller height the lower selector is partially clipped initially, but keyboard focus scrolls it into view, and Escape returns focus to Import audio. The title refactor was also inspected in the AI post-processing and Assistant mode dialogs, including the Beta chip. Audio selection, native file import, retranscription and real OS zoom were not exercised.

## Inline dictionary validation

A related glossary-validation case from [virtaal #4334](https://github.com/translate/virtaal/issues/4334) prompted testing inline edits, not only the Add dialog. In the browser preview, clearing a replacement's original term and blurring it showed a red field but still saved the whitespace; it remained blank after navigating away and back. Inline edits now refuse whitespace-only source terms and replacement values while retaining the editable draft, and explain that changes were not saved. Existing field names are also available after the placeholder disappears. The error is associated with its field, and both fields stay aligned when one has a message. Tests cover empty original, empty replacement, correction, and a glossary term with no replacement. The message was translated in all supported locales.

At 800×600, invalid original, replacement and glossary drafts were inspected and navigating away/back restored the previously saved values; a corrected original was also inspected. This verifies the browser preview's repository, not native persistence. At 400×300, a separate keyboard pass found that tabbing from Add to the first row can leave the focused field below the viewport while the tall list header remains expanded. That pre-existing shared scrolling behavior remains to investigate; the small-viewport captures are not counted as a successful keyboard-visibility check.

The 400×300 focus-visibility problem above was traced to the expanding sticky scroll-list header: at short heights it could cover the whole available list area, and collapse during automatic focus scrolling could leave the target below the viewport or behind the header. At viewport heights of 420 CSS pixels or less, populated list headers now scroll normally instead of sticking and shrinking; a small scroll-padding reserve helps keep focused controls and their nearby errors visible. The title, description and action remain in the scrollable content. A CSS-emission regression test covers the short-height rules; jsdom cannot prove their layout.

In Chromium preview at 400×300, keyboard focus on the first Dictionary original, replacement, delete and glossary controls was visible with both normal and reduced motion; a blank-original error remained visible when tabbing to its replacement. At 800×400, five consecutive focus stops were checked in each of Dictionary, History and Styles. Short-height History scroll and normal-height 800×600 sticky-header behavior were inspected separately. These checks do not verify native WebView zoom, other locales, or every list state; the small-height treatment intentionally lets the page title and action scroll out of view rather than cover content.

## Dictionary deletion and keyboard focus

Following the focus-loss case in [garret #145](https://github.com/iuliandita/garret/issues/145), deleting a Dictionary row with Enter was reproduced in Chromium preview: the focused button disappeared and focus fell to the document body. Keyboard deletion now moves focus to a surviving next or previous removable row, or Add if none remain, without overriding focus deliberately moved elsewhere. Pointer deletion does not force a new focus target. Browser captures were inspected for first and successive last-row deletions at 800×600 and 400×300, including the final Add focus; a pointer deletion was also checked. Tests cover neighboring focus, fallback and focus moved elsewhere. Context-menu activation, global-only entries, native WebView and screen-reader speech were not visually verified.

A separate deferred-request test reproduced a data race: when one deletion failed after another succeeded and a term was added, restoring an old whole-list snapshot resurrected the deleted ID and hid the new term. Rollback now restores only the failed entry relative to surviving neighbors and preserves a newer copy if one exists. Tests cover both concurrent deletion/addition and a newer same-ID copy; browser preview did not inject repository failures.

The tray's Copy last transcript action queried the newest database row directly, including a row hidden during the Undo window. It now selects the newest non-pending row and restarts the lookup if deletion state changes during a paginated read. Unit tests cover a pending newest row, multiple pages, changing deletion state and no visible rows. Native tray and clipboard behavior were not exercised in browser preview.
