# Review the diff that will actually be pushed

1. Install the repository's [pinned Lefthook hooks](../CONTRIBUTING.md#commit-and-pull-request-conventions) and confirm the pre-push hook is active. Merge the current tip of the actual PR base as required by `AGENTS.md`, run the applicable gates and commit the final tree. A stack's base is not necessarily `main`.
2. Run `node scripts/ci/standards-review.mjs prepare <PR-base-branch>`. It fetches that branch from `origin`, requires it to be contained in `HEAD`, and prints a directory inside the worktree's Git metadata. Nothing in it belongs in a commit. `standards.md` is the committed policy; `changes.patch` is the complete binary-inclusive PR diff, not the staged patch or just the outgoing commits.
3. Read both files **in full**. Split large files into consecutive ranges; inspect binary assets with their appropriate viewer and submodule commits in the submodule. Use the working tree to trace callers. If the standards changed, review the policy delta too. In `receipt.md` keep the commit/blob identities and fill every numbered row. Write `verified: <what was checked, where and with what result>` or `not applicable: <what in this diff puts it outside the rule>`. Cite at least one changed path in backticks, relative to the repository root, and give each rule its own observation. For example: ``- CS02: verified: `apps/desktop/src/repos/api-key.repo.test.ts` reloads the wire value captured on update.`` An empty diff takes only `not applicable` rows. A blocker means fix, recommit, prepare and review again, not fill a row with "pending".
4. Push. The hook checks Git's **outgoing** commit IDs and the current remote base, checks all dispositions, and consumes the receipt for this push attempt. It leaves `last-review.md` for filing. A rejected push, another commit or a base update requires a fresh review. Ref deletion and no-op pushes have no diff. Push exactly the reviewed commit to the same-named branch on `origin`; do not combine it with a tag or another branch update.
5. Paste `last-review.md` in place of the verification heading, base/head lines and first fold of the PR template. Keep the verification command results below it. After a push, `synchronize` can go red until you update the description; the `edited` event rechecks it. Retargeting is a new base, even if the commit IDs happen to match.

**What is enforced.** The `Full-diff coding standards review` PR job checks the event's base and head, ancestry, standards blob and one disposition for every numbered section. Removing a section from the new standards still requires accounting for its base ID. Both gates also diff the migration SQL against the actual base: modifying, deleting or renaming an existing migration fails even with a complete receipt. Add a forward migration instead. This protects databases on stacked branches too; it does not prove that the new migration was registered or that an upgrade succeeds. The PR job has no changed-path filter, secrets or write permission. The checker comes from the immutable base except on the first installation, when neither the file nor the policy exists there. The proposed checker runs its own negative tests separately. A hook can be bypassed; a green receipt is an attestation, not proof of someone's thought process. Review the evidence in each row.

**Repository administrator:** require the status `Full-diff coding standards review` for each protected target, including a stacking base if it accepts merges. Require the PR to be up to date with its target before merge: a green check describes the base at the time of the event, not a base that advances afterwards. Protect the workflow and policy themselves with independent review. A workflow in a branch does not modify remote branch protection. Keep the existing `Folded Body Check`; it tests the shape of the description, not this attestation.
